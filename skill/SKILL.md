# Audit AI Reconciliation

ระบบควบคุมงานออดิทของแผนกตรวจบัญชีฝาก-ถอน ทำหน้าที่กระทบยอด **STM (ฝั่งธนาคาร)** กับ **BO (รายงานหลังบ้าน)** ข้ามหลายบริษัทในเครือ แล้วออกเอกสารชี้แจงและสรุปความเสียหาย

เอกสารนี้เก็บ **ความรู้เชิงธุรกิจที่เดาเองไม่ได้** เป็นหลัก ส่วนรายละเอียดโค้ดอยู่ใน `references/`

---

## กฎเหล็ก 5 ข้อ (เคยพลาดมาแล้วทั้งหมด)

1. **สายชี้แจงมาจาก "ระบบต้นทางของบริษัท" ไม่ใช่ความรุนแรง** — เคยเดาว่า critical/high = รายวัน ซึ่งผิด ดูหัวข้อ "2 ระบบ" ด้านล่าง
2. **ห้าม push ข้อมูลจริงขึ้น GitHub** — repo `nalatikana/Audit-Reconciliation-Control` เป็น **Public** ข้อมูลบัญชีลูกค้าจริงห้ามขึ้นเด็ดขาด `.gitignore` กัน `*.pdf` `*.docx` ไว้แล้ว
3. **`service_role` key ของ Supabase อยู่ใน n8n เท่านั้น** — หน้าเว็บใช้ได้แค่ `anon` key เพราะ service_role ข้าม RLS ทั้งหมด
4. **ชื่อไฟล์ดาวน์โหลดต้องเป็น ASCII** — ชื่อไทยทำให้ Chromium ตั้งชื่อไฟล์เป็น "download" เฉยๆ ใช้ `FILE_SLUG` map หรือ `asciiSlug()`
5. **`device_bash` ลบไฟล์บนเครื่องผู้ใช้ไม่ได้** — `rm` จะได้ "Operation not permitted" ให้ `mv` เข้าโฟลเดอร์ `_to_delete/` แทน (ใช้กับ `.git/index.lock` บ่อย)

## 2 ระบบที่แผนกตรวจ

แผนกตรวจอยู่ 2 ระบบ แต่ละระบบมีจังหวะส่งชี้แจงคนละแบบ **สิ่งที่กำหนดว่าเคสไปทางไหนคือบริษัทต้นทางอยู่ระบบไหน**

| ระบบ | จังหวะส่ง | ใครชี้แจง | กำหนดส่งคืน |
|---|---|---|---|
| **XB** | ทุกวัน ภายใน **17:00** — **ทุกเคส ไม่ดูความรุนแรง** | หัวหน้ากะ | 24 ชม. |
| **123** | รวบเป็นรอบ **1-15 / 16-25 / 26-สิ้นเดือน** | ออดิท 1 / 2 / 3 ตีไฟล์ให้ชี้แจง | 2-3 วันหลังปิดรอบ |

"123" ในที่นี้คือ **พนักงานออดิท 1 2 3** ไม่ใช่รหัสระบบ

การแมปบริษัท→ระบบ เก็บที่ `DB.companies[].system` (`"XB"` / `"SYS123"` / `null`) ตั้งได้จากหน้า **งานชี้แจง** ผู้ใช้ยังไม่ได้ยืนยันว่า AT4/SK8/FR8 ตัวไหนอยู่ระบบไหน — ถ้าจำเป็นต้องรู้ ให้ถาม อย่าเดา

บริษัทที่ยังไม่ได้กำหนด → จัดเป็นรายรอบไว้ก่อน (เคสไม่หาย) แล้วขึ้นแถบแดงเตือน

**อีเมล**: กล่อง `work.ltd89@gmail.com` label **AUDIT 2** ส่งต่อมาจาก `faz123u3@gmail.com`

หัวข้อเมลมี 2 แบบ ใช้แกะบริษัทกับวันที่:
```
Fwd: AT4 ส่งตรวจบัญชีฝาก - ถอนและไฟล์ต่างๆ ประจำวันที่ 20-07-69 เรียบร้อยครับ
Fwd: SK8 ส่งตรวจบัญชีเพิ่มเติมประจำวันที่ 18-07-69 เรียบร้อยครับ    ← มีคำว่า "เพิ่มเติม"
```
วันที่เป็น **dd-mm-yy พ.ศ. 2 หลัก** (`69` → `2569` → ค.ศ. `2026`)

**บริษัท**: AT4, SK8, FR8 (ข้อมูลตัวอย่างในระบบใช้ SYS123)

**ช่องทาง PM**: Cyberplus, AUTOPEER, AZPAY — อยู่ในคอลัมน์ `ชื่อธนาคาร` รูปแบบ `Cyberplus-4 : Cyberplus` (เทอร์มินัล : ช่องทาง) ถ้าเทอร์มินัลเป็นตัวเลข 9-15 หลักแปลว่าเป็นเลขบัญชีธนาคารจริง

> **ข้อจำกัดใหญ่ที่สุดของโปรเจกต์**: ช่องทาง PM คิดเป็น ~97% ของยอดรายวัน แต่**ยังไม่มีไฟล์ statement ฝั่งธนาคารของช่องทางเหล่านี้** ระบบจึงตรวจได้จริงแค่ 128 จาก 4,670 รายการ รายการ PM ที่ไม่มีฝั่ง STM **ไม่นับเป็น exception** แต่แสดงในตาราง "ช่องทางที่ยังไม่มีไฟล์ฝั่งธนาคาร" — อย่าไปแก้ให้มันขึ้นเป็น exception

รายละเอียดหัวคอลัมน์เป๊ะๆ อยู่ใน `references/file-formats.md` — อ่านก่อนแตะตัว parser

## กฎการจับคู่และกฎธุรกิจ

**จับคู่ 4 จุด**: บัญชี + เวลา + ยอด + (ธนาคาร/เลขท้ายบัญชีลูกค้าที่ระบุในสลิป)

จุดที่ 4 อ่านจากคำอธิบายใน statement เช่น `จาก GSB X3463 ...` / `รับโอนจาก KBANK x4845 ...` แล้วเทียบกับ `ชื่อธนาคารสมาชิก` + เลขท้ายบัญชีฝั่ง BO

**กฎรายธนาคาร**
- SCB: `X1` = รับเงิน, `X2` = โอนออก, `XB` = ปรับปรุงยอด (แยกออกจากการจับคู่)
- KBANK: กรองบรรทัด "ยอดยกมา" / "ยอดยกไป"
- GSB: กรอง "รอบวันที่", `Transfer SAV Deposit` = รับเงิน
- **KBANK/SCB ให้เวลาแค่ HH:MM** → tolerance ต้องมีพื้นอย่างน้อย 60 วินาที (`settings.minuteTolerance`)
- ทิศทางใช้ **ผลต่างยอดคงเหลือ** เป็นหลัก ตกไปใช้ code/ข้อความเป็นตัวสำรอง

**กฎธุรกิจที่ตรวจได้โดยไม่ต้องรอ statement** (`rules.js`)

| รหัส | กฎ |
|---|---|
| `comm_cut_missing` | ค่าคอมสะสมเกินแต่ไม่มีรายการตัดยอด |
| `comm_cut_mismatch` | ยอดตัดเครดิต ≠ ส่วนต่างค่าคอม |
| `credit_orphan` | ตัดเครดิตโดยไม่มีคำขอถอนค่าคอม |
| `credit_math` | เครดิตก่อน − ตัด ≠ เครดิตหลัง |
| `bonus_math` | ยอดก่อน + เครดิต + โบนัส ≠ ยอดหลัง |
| `cross_day` | วันที่ทำรายการ ≠ วันที่ธนาคาร |
| `duplicate` | รายการที่**คนกดเอง** (เติมมือ/ถอนมือ) ซ้ำในช่วงสั้น — auto ที่ลูกค้าฝากซ้ำเป็นเรื่องปกติ อย่าฟ้อง |
| `large_amount` | **ถอน**เกินเกณฑ์ (ค่าเริ่มต้น 100,000) |

ระบบดึงตัวเลขจากหมายเหตุที่พนักงานพิมพ์เองได้ เช่น `"ได้รับยอดภายในเดือน 21 บาท สะสมเกิน 79 บาท"` และ `"สะสมเกินเดือน ได้รับจริง 108 บาท"` — คำเขียนไม่คงที่ ต้องรองรับหลายรูปแบบ

## ค่าเงิน USDT

ระบบมีทั้งบาทและ USDT (เช่น ถอนจาก Azpay เป็น USDT เข้าหลัก B10) **ยอดที่เป็น USDT ต้องอ้างอิงเรตของวันที่เกิดรายการเสมอ** จึงต้องบันทึกเรตทุกวันและเก็บ log

- **กรอกเองเป็นหลัก** — เรตที่ถูกต้องคือเรตที่บริษัทใช้ปิดยอดจริง ระบบ**ไม่**เอาเรตจากเว็บมาใช้แทน
- ดึงเรตตลาดมาแสดงเทียบ 3 แหล่ง: Bitkub `api/v3/market/ticker?sym=usdt_thb`, `open.er-api.com/v6/latest/USD`, CoinGecko
- แก้ย้อนหลังได้แต่ไม่ทับของเดิม — เก็บลง `revisions` + Audit Log
- ห่างจากตลาดเกิน 2% เตือนแดง, นอกช่วง 1–1,000 บาท/USDT บันทึกไม่ได้
- วันที่ไม่มีเรต → ใช้ของวันล่าสุดก่อนหน้าและขึ้นสถานะเหลือง

## กับดักที่เสียเวลาไปแล้ว

| อาการ | สาเหตุจริง |
|---|---|
| คอลัมน์ใน xlsx เลื่อนไปทั้งแถว | regex `<c ...>` ต้อง **non-greedy** และรองรับแท็กปิดในตัว `<c r="E2"/>` |
| BO/PM อ่านได้ 0 แถว "ไม่มีเวลาที่อ่านได้" | ใน header DICT ต้องวาง `datetime` **ก่อน** `date` ไม่งั้น `วันที่ทำรายการ` โดน `วันที่` ชิงไปก่อน |
| `wrong_bank` ฟ้อง 126 รายการ | เทียบธนาคารของ**ลูกค้า**กับ master ของบัญชี**บริษัท** — คนละอย่างกัน |
| ชื่อไฟล์ใน zip เป็นตัวประหลาด | zip ไทยใช้ cp874 ไม่ใช่ utf-8 — เช็ค EFS flag (bit 11) ก่อน |
| ภาพที่จับจากหน้าจอโดนตัด | `STYLE_PROPS` ต้อง**ไม่**คัด `width`/`height`/`max-height`/`overflow` เพราะ `getComputedStyle` คืน content-box แต่ `box-sizing: border-box` ถูกคัดไปด้วย |
| กราฟเรต USDT เป็นเส้นแบน | ค่าแกว่งแค่หลักสตางค์แต่ไกลจากศูนย์ — ต้องใช้ `zoomY: true` |
| CDN โหลดไม่ได้ | ทุกอย่างต้องมีทางสำรองในตัว — เขียน xlsx reader/writer เอง ฝัง pdf.js ใน `vendor/` |
| exception ซ้ำ 2 รายการ | กฎธุรกิจกับการจับคู่จับเคสเดียวกันได้ — ยุบด้วย key `type|account|time|systemAmount` เก็บอันที่มี `detail` |
