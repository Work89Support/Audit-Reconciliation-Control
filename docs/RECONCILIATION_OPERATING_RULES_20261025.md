## 0. ข้อสรุป Final ที่ผู้ใช้ยืนยัน 26 ตุลาคม 2026

- ให้รอบอัตโนมัติทำงานต่อผ่าน Dispatcher ที่อนุมัติเท่านั้น โดยผลที่ไม่ผ่าน Quality Gate ต้องหยุด `needs_review` และผล `ready` ยังไม่เป็นผลหลักจนกว่าผู้มีสิทธิ์ยืนยัน
- 7M ปิดเคสจากคู่ STM/PM ↔ BO ได้เฉพาะ **บัญชีเดียวกัน** และทิศทางการเคลื่อนไหวจริงตรงกัน: เงินออก ↔ BO ปรับออก, เงินเข้า ↔ BO ปรับเข้า
- ความสัมพันธ์การโอน A → B ใช้เชื่อมเคสและเก็บเป็นหลักฐานการโอนภายในได้ แต่ห้ามใช้แทนคู่ STM/PM ↔ BO ของบัญชี A หรือ B และห้ามใช้ความสัมพันธ์ A → B ปิดสองเคสโดยตรง
- `Keep -` เป็นข้อมูลประกอบทุกกรณี: ไม่เข้ายอด ไม่สร้าง Exception และไม่เปิดเคส; หากข้อมูลไม่ครบให้แสดงคำเตือนในส่วนข้อมูลประกอบเท่านั้น
- หมด SLA ให้แจ้งเตือน/ยกระดับเท่านั้น ห้ามสร้างหรือยืนยันยอดเสียหายอัตโนมัติ
- การปิดเคสต้องเลือกผลชัดเจนหนึ่งข้อ: (1) ไม่เสียหายและไม่พบความผิดพลาด (2) ไม่เสียหายแต่ทำงานผิดพลาด (3) ยืนยันความเสียหาย
- OCR ต้องผ่าน Golden dataset, รักษา source row และผ่าน confidence/control checks ของวันที่ เวลา ทิศทาง ยอด และบัญชี; ถ้าฟิลด์สำคัญไม่ผ่านให้หยุด `needs_review` และห้ามปิดเคส

## 3. Preflight ก่อนรันทุกครั้ง

1. ตรวจวันที่ธุรกิจและบริษัทในหน้ารันให้ตรงกับชื่อไฟล์
2. ตรวจว่าไม่มี execution ของบริษัท/วันเดียวกันสถานะ `queued` หรือ `running`
3. ตรวจไฟล์ครบตามกลุ่มของบริษัท และทุกไฟล์อ่านได้จริง ไม่ใช่แค่มีชื่อไฟล์
4. ถ้า parser อ่านไม่ครบ, PDF/OCR ไม่ครบหน้า, หัวคอลัมน์ไม่รู้จัก หรือยอดควบคุมไม่ตรง ให้หยุดที่ `needs_review`; ห้ามตีความเป็นศูนย์รายการ
5. ตรวจ Quality Gate ก่อนยืนยันผลหลัก: แหล่งข้อมูลไม่ซ้ำ, วันถูกต้อง, จำนวนแถวไม่หาย, exception ไม่ถูกตัดทิ้ง, และ source-ready ครบ
6. ผล `ready` คือพร้อมทบทวน ไม่ใช่ผลหลัก จนผู้มีสิทธิ์กดยืนยัน
7. ห้ามกระทบเคสที่ปิดแล้ว ผลที่อนุมัติแล้ว ประวัติ หลักฐาน หรือยอดเดิม เว้นแต่มีคำสั่งย้อนผลเฉพาะรายการ

### 3.1 กฎ OCR/PDF ที่ต้องผ่านก่อนอนุญาตให้กระทบยอด

- PDF ที่มี text layer ให้อ่านตรงก่อน; ใช้ OCR เฉพาะไฟล์สแกน/ภาพที่อ่านข้อความตรงไม่ได้
- OCR/การถอดภาพต้องผูกกับ checksum, source file, บริษัท, วันที่, บัญชี, เลขหน้า และแถวต้นทาง ห้ามใช้ผลจากไฟล์คนละเวอร์ชัน
- ตรวจจำนวนหน้า จำนวนแถว ยอดฝาก ยอดถอน และสมการยอดคงเหลือรายหน้า; ถ้าไม่ครบหรือไม่สมดุลให้หยุด `needs_review` ห้ามคืนค่าเป็นศูนย์
- รายการเวลาและยอดซ้ำต้องเก็บเป็นคนละแถวเมื่อ source row/reference ต่างกัน; ตัดได้เฉพาะภาพหน้าซ้ำหรือแถวต้นทางเดียวกันที่พิสูจน์ได้
- TMN/SCB ที่ต้องตรวจภาพใช้ reviewed payload เท่านั้น และต้อง reject เมื่อ hash, จำนวนหน้า, row id, เวลา, ยอด หรือยอดคงเหลือไม่ตรงหลักฐาน

## 4. ข้อมูลประกอบที่ไม่กระทบยอดและไม่สร้างเคส

- `เก็บ` / `Keep -`
- `ฝาก AFF`
- `ถอน AFF`
- `โบนัส`
- `ยกเลิก`

ต้องเก็บแถวดิบและหลักฐานไว้ให้ตรวจย้อนหลัง แต่แยกเป็นข้อมูลประกอบ ไม่รวมยอด STM/PM หรือ BO ที่ใช้จับคู่ และไม่สร้าง exception

แถว `เก็บ`/`Keep -` ต้องอยู่ในส่วนข้อมูลประกอบเสมอ แม้หาคู่ฝากจริงไม่ได้หรือกำกวม: แสดงคำเตือนข้อมูลประกอบได้ แต่ห้ามนำเข้ายอด ห้ามสร้าง Exception และห้ามเปิดเคส

## 5. กฎร่วมทุกบริษัท

- เริ่มจากรายการ BO ที่เป็นธุรกรรมจริง แล้วเทียบกับ STM/PM ที่อ่านได้ทั้งหมดในขอบเขตบริษัทและวันเดียวกัน
- ใช้บริษัท บัญชี/Provider ทิศทาง ยอด วัน และ identity/reference ที่มีจริงเป็นเงื่อนไข ห้ามจับจากยอดอย่างเดียวเมื่อมีหลายตัวเลือก
- ชื่อ Provider ต้อง canonicalize ก่อนจัดกลุ่ม เช่น `ATP PAYMENT ... 00000ATP` = `AUTOPEER`, `CP2/CPPAY/CPXM` = `COREPAY`, `CYBER/CBY` = `CYBERPLUS`
- Canonicalize เพื่อจับคู่และแสดงกลุ่มเท่านั้น ต้องเก็บชื่อดิบ แถว ยอด ไฟล์ และประวัติเดิมครบ
- รายการที่เวลาและยอดซ้ำกันอาจเป็นธุรกรรมจริงหลายรายการ ต้องเก็บแยกตาม source row/reference; ตัดได้เฉพาะกรณียืนยันว่าเป็นไฟล์หรือแถวต้นทางเดียวกันซ้ำจริง
- เคสข้ามวันต้องมีวันที่จริงทั้ง BO และ STM/PM; ช่วง `23:00–23:59` ต้องตรวจหลักฐานวันถัดไปก่อนปิด

### 5.1 ชื่อหัวบัญชีและการรวมหน้า Audit ตาม BO

- ใช้ชื่อบัญชีดิบจาก BO เป็นหัวหน้าสรุปและหน้ารายละเอียดเสมอ โดยรองรับทั้งผลรุ่นใหม่ที่เก็บใน `boAccountLabel` และแถว BO ที่อ่านจากไฟล์ซึ่งเก็บชื่อไว้ใน `account`
- ชื่อมาตรฐานของ Provider ใช้เป็น identity สำหรับค้นหาและรวมข้อมูลเท่านั้น เช่น `AUTOPEER`, `COREPAY`, `CYBERPLUS`, `MYPAY`; ห้ามนำชื่อมาตรฐานมาสร้างหัวทั่วไปซ้ำ หากพบหัว BO จริงของ Provider และทิศทางเดียวกันแล้ว
- ก่อนสร้างกลุ่มสำรอง ต้องนำรายการผลเก่าและ STM/PM ที่ใช้ชื่อ Provider มารวมเข้าหาหัว BO จริงด้วย `บริษัท + Provider + ทิศทาง` เมื่อพบปลายทางที่ตรงเพียงหัวเดียว
- ห้ามแสดงหัว `STM/PM ไม่มี BO · ...` เมื่อมีแถว BO จริงของ Provider และทิศทางนั้นอยู่แล้ว ให้แสดงหัวนี้เฉพาะกรณีที่ตรวจไฟล์ต้นทางแล้วไม่พบ BO ที่รับรายการได้จริง
- ถ้าพบหัว BO ได้มากกว่าหนึ่งหัวและไม่มี identity เพียงพอ ห้ามเดาหรือรวมจากยอดอย่างเดียว ต้องคงเป็นรายการรอตรวจเพื่อรักษาหลักฐาน
- กฎนี้ใช้ร่วมกันครบ 9 บริษัท: `3XB`, `MC8`, `MR9`, `PS8`, `UR9`, `AT4`, `FR8`, `SK8`, `UFABET7M`
- การรวมชื่อเป็นการจัดหน้าแสดงผลและ Export เท่านั้น ห้ามรันกระทบยอดใหม่ เปลี่ยนคู่ ยอด เคส สถานะ ประวัติ หรือหลักฐานเดิม
- ตรวจ Production วันที่ `2026-10-26` แล้ว: ทุกบริษัทใช้หัว BO จริง และไม่พบหัว Provider ทั่วไปหรือ `STM/PM ไม่มี BO` ซ้ำในกรณีที่มี BO จริง ([PR #82](https://github.com/Work89Support/Audit-Reconciliation-Control/pull/82))

## 6. เงื่อนไขรายเครือ

### เครือ XB: 3XB, MC8, MR9, PS8, UR9

- `ยืมข้ามบริษัท` และรายการภายในไป USDT เป็นข้อมูลประกอบ ไม่สร้างเคสความเสียหายจากการไม่มีคู่ปกติ

### เครือ 123: AT4, FR8, SK8

- เวลาอ้างอิงหลักจาก BO คือคอลัมน์ **`วันที่ธนาคาร`** เท่านั้น ห้ามย้อนใช้ `วันที่ทำรายการ` เมื่อ `วันที่ธนาคาร` ว่าง
- บัญชี/Provider ใหม่ต้องอ่าน identity จาก BO แล้วสร้าง coverage; ห้ามจำกัดเฉพาะรายการ master เก่า
- ไฟล์ PM ใช้เวลาที่ตกลงตาม Provider/direction และยอดจริงที่จ่ายหรือรับสำเร็จ ไม่ใช้ยอดที่ขอเมื่อมี actual amount
- KTB ปกติใช้ `บริษัท + บัญชี + ทิศทาง + วันที่ธนาคาร + เวลาธนาคาร + ยอด` และต้องเป็นคู่ 1:1; ห้ามใช้เวลาสร้าง BO แทน
- KTB ข้ามวัน: BO วันที่ D เวลา 23:00–23:59 ค้น STM เฉพาะวันที่ D+1 เพิ่มได้ โดย STM วันถัดไปเป็นเวลาใดก็ได้ เช่น 00:xx หรือ 01:42; ไม่บังคับให้เวลา BO/STM ใกล้กัน
- คู่ KTB ข้ามวันต้องตรงบริษัท บัญชี ทิศทาง และยอดแบบ 1:1 ชัดเจน เก็บวัน–เวลาจริงทั้งสองฝั่ง ปิดเคสเดิม และห้ามสร้างเคสซ้ำใน D+1
- ถ้าพบ STM แล้วแต่มีหลายคู่ ยอด/ทิศทาง/บัญชีขัดกัน หรือ parser อ่านวัน เวลา ยอด หรือบัญชีไม่ครบ ให้เป็น `เคสข้ามวัน`/`พบ STM แต่จับคู่ไม่ได้` และหยุด `needs_review`; ห้ามแสดงว่า `รอ STM/PM` และห้ามปิดอัตโนมัติ
- เอกสารสรุปทุกบัญชีเรียง `รายการ STM/PM → BO → ผล Audit` เสมอ รวมถึงบัญชีใหม่

### UFABET7M / 7M

- ชื่อหัวบัญชีแสดงตาม BO; ตัวอย่างที่ยืนยันแล้ว:
  - `ATP PAYMENT ถอน 00000ATP`

  - `CYBERPLUS PAYMENT ถอน 00000CYBERPLUS`
  - `CYBERPLUS PAYMENT ฝาก 00000CYBERPLUS`

  - `ฝาก SCB สมภพ 5034633891`
  - `ฝาก/ถอน TMN รุ่งฟ้า 0812792075`
  - `ฝาก/ถอน TMN สรวิศา 0639274201`
- ถ้ามีบัญชีใหม่ ให้เพิ่มจากชื่อ BO ดิบ ไม่เดาชื่อเอง
- TMN PDF/ภาพต้องอ่านครบทุกหน้าและทุกแถว; รายการเวลา/ยอดเท่ากันต้องเก็บทุก occurrence ตามตำแหน่งแถว ไม่รวมทิ้ง
- PM 7M ใช้ Ref + User + Amount แบบหนึ่งต่อหนึ่งเมื่อมี; เวลาใช้ช่วยแยกกรณีกำกวม
- `Keep -` เป็นข้อมูลประกอบ ไม่กระทบยอดและไม่สร้างเคส
- จับคู่รายการภายในบริษัทเป็นงานปิดเคส ไม่ใช่การกระทบยอดใหม่ โดยต้องครบทุกข้อ:
  - 7M บริษัทเดียวกัน วันเดียวกัน สกุล THB
  - คู่ที่ใช้ปิดเคสต้องเป็นบัญชีเดียวกันระหว่าง BO กับ STM/PM
  - ยอด BO เท่ากับยอด STM/PM
  - เวลาห่างไม่เกิน 5 นาที
  - มีต้นทางจริงทั้งสองฝั่ง, source-ready, ไม่ถูกจอง, ไม่ถูกแทนด้วยเคสรุ่นใหม่ และไม่มีทะเบียนความเสียหาย
  - STM `ถอน/โอนออก` ต้องพบ BO raw ของบัญชีเดียวกันเป็น `ปรับยอดออก/โยกออก/โอนออก`
  - STM `ฝาก/รับเข้า` ต้องพบ BO raw ของบัญชีเดียวกันเป็น `ปรับยอดเข้า/โยกเข้า/โอนเข้า/รับยอด`
  - ปิดสองเคสพร้อมกันและบันทึก Audit โดยไม่แก้ `system_amount` หรือ `bank_amount`
  - ความสัมพันธ์ A → B ให้เชื่อมเคสและแนบหลักฐานการโอนภายในได้ แต่ทั้งสองบัญชียังคงต้องมีคู่ STM/PM ↔ BO ของตนเองก่อนปิด; ห้ามใช้ขา A แทนขา B หรือปิดจากความสัมพันธ์ข้ามบัญชีโดยตรง

## 8. รันมือและการยืนยันผล

- เลือกบริษัท วันที่ และไฟล์จากหน้ารันมือให้ชัดเจน; กฎ parser/matching ต้องเหมือนรอบอัตโนมัติ
- รันมือสำเร็จต้องได้ผล `ready` และสามารถสร้าง/แสดง exception จากผลรอบนั้นได้
- ก่อนยืนยันผลหลัก ตรวจจำนวน STM/PM, BO, จับคู่, เหลือตรวจ, breakdown ของ exception และ Quality Gate

## 9.1 SLA และผลปิดเคส

- หมด SLA คือเหตุแจ้งเตือนและยกระดับให้ผู้รับผิดชอบ/หัวหน้าตรวจ ไม่ใช่หลักฐานความเสียหาย
- ห้ามระบบสร้างยอดเสียหาย ยืนยันความเสียหาย หรือเปลี่ยนผลปิดเคสจากเวลา SLA โดยอัตโนมัติ
- ผู้ปิดเคสต้องเลือกผลหนึ่งข้อและบันทึกผู้เกี่ยวข้อง/กะ/เหตุผล/หลักฐานตามสิทธิ์:
  1. `ความเสียหาย 0 บาท / ไม่พบความผิดพลาด`
  2. `ความเสียหาย 0 บาท / แต่มีการทำงานผิดพลาด`
  3. `ยืนยันความเสียหาย`
- ผลข้อ 2 ต้องคงอยู่ในทะเบียนเพื่อใช้พิจารณาภายหลัง แม้ยอดเสียหายเป็นศูนย์

## 9.2 OCR Golden dataset และเกณฑ์หยุด

- Golden dataset ต้องครอบคลุมตัวเลขที่เคยสับสนอย่างน้อย `10 ↔ 1,000`, `40 ↔ 4,000`, `53 ↔ 953`
- ยอด `4,000` เวลา `08:44` สอง occurrence ต้องคงเป็นคนละ source row แม้ภาพ เวลา และยอดเหมือนกัน
- ต้องทดสอบภาพตัดขอบ หน้าเรียงผิด/ขาด และ OCR ที่คืนชื่อ เวลา และยอดแยกเป็นคนละกลุ่ม
- ต้องเก็บ confidence/validation ของวันที่ เวลา ทิศทาง ยอด และบัญชีแยกกัน ไม่ใช้คะแนนรวมค่าเดียวกลบฟิลด์สำคัญ
- Confidence เพียงอย่างเดียวไม่อนุญาตให้ปิดเคส: ต้องมี source row/page/checksum และ control total หรือสมการยอดคงเหลือที่ผ่านด้วย
- ฟิลด์สำคัญใดไม่ผ่าน threshold ของ parser profile หรือหลักฐานควบคุมไม่ครบ ให้หยุด `needs_review` และห้ามปิดเคส/บันทึกความเสียหายอัตโนมัติ
